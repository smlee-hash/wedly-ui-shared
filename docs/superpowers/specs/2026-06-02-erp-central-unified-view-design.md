# ERP 중앙 통합 — "통합 보기" 공용화 설계서

> **작성일:** 2026-06-02
> **상태:** 설계 확정(사용자 승인: "제안한 로드맵대로 진행해"). 1단계 구현 대기.
> **이 문서가 다루는 범위:** 전체 3단계 로드맵 + **1단계(공용 토대)** 상세 설계. 2·3단계는 개요만(각자 별도 설계서로 진행).

---

## 1. 목표 (한 문장)

ERP·하이브·일루아 세 앱의 "통합 보기" 화면을 **하나의 공용 부품**으로 모아, 한 번 고치면 세 곳에 똑같이 반영되게 한다. 그 첫 단추로 ERP에도 통합 보기를 띄운다.

## 2. 왜 하는가 (현재의 불편)

- 지금은 기능 업데이트가 **하이브에만** 반영되고, ERP·일루아는 뒤처진다.
- 통합 보기의 "큰 화면" 코드는 **하이브·일루아가 각자 복사본**을 갖고 따로 논다. ERP는 그 기능이 아예 없다.
- 결과적으로 같은 일을 세 번 해야 하고, 데이터 관리도 앱마다 따로 해 번거롭다.

## 3. 확인된 사실 (추측 아님 — 실제 코드 확인)

조사로 확인한, 설계의 토대가 되는 사실들:

1. **세 앱은 이미 같은 데이터베이스 하나를 공유하고, 그 주인은 ERP다.**
   하이브·일루아는 ERP가 소유한 테이블(예: 경정청구 데이터, 설정 보관용 테이블, 업로드, 통화 사례 등)을 "읽고 쓰기만" 하며 구조 변경(마이그레이션)은 못 한다. 일루아 스키마 주석에 "DB owner는 ERP" 명시.
   → **데이터를 ERP로 "옮기는" 작업은 필요 없다.** ERP엔 이미 다 있다.

2. **ERP는 모든 영역(경정청구·정부지원금·노무·무상·정책자금 등)을 자기 데이터로 직접 갖고 있다.**
   하이브는 다른 영역 데이터를 ERP의 외부 조회 주소를 통해 "빌려" 읽지만, ERP는 직접 읽으면 된다(더 단순·빠름).

3. **ERP에 새 페이지는 기존 '통합 DB 관리' 페이지(`/unified-db`)를 안 건드리고 폴더 하나로 깔끔히 추가된다.**
   ERP는 `(erp)` 라우트 묶음 + 공용 레이아웃 + 페이지별 접근 가드 구조라, 폴더만 만들면 로그인·권한이 자동 적용된다.

4. **"한 번 고치면 세 곳 동일"은 지금 자동이 아니다.**
   - 하이브·일루아는 공용 부품(`@wedly/ui-shared`, `@wedly/detail-modal-shared`)의 *일부 작은 부품*만 공유한다(셀 입력기·드래그 섹션·관리자 메뉴 등). **통합 보기 "큰 화면" 자체는 각 앱의 복사본**이다.
   - 공용 부품은 GitHub의 최신 상태를 그대로 가져오는 방식(버전 고정 없음)이라, 한 곳을 고쳐도 **각 앱이 다시 설치(install)해야** 반영된다. 자동 전파 장치는 없다.
   - **ERP는 이 공용 부품을 아예 쓰지 않는다**(자체 방식). 따라서 ERP를 공용화에 합류시키려면 별도 준비가 필요하다.

5. **하이브와 일루아의 통합 보기 구조는 매우 유사하다.** 차이는 주로 "메인 영역이 무엇이냐"(하이브=경정청구, 일루아=정부지원금)와 로그인 체계, 그리고 영역 목록·정산 항목 같은 앱별 값들뿐이다.

## 4. 핵심 설계 원칙

- **표시만 손대고 데이터·권한은 안 바꾼다.** 순서·이름·화면 구성은 표시 설정이며, 어떤 영역을 편집할 수 있는지는 "위치"가 아니라 "영역 키"로 판단한다(순서를 바꿔도 다른 팀 자료가 편집되지 않음 — 하이브에서 이미 검증된 원칙).
- **잘 돌던 것을 먼저 흔들지 않는다.** 새 위험은 새로 만드는 ERP 쪽으로 몰고, 하이브·일루아 전환은 가장 마지막(3단계)에 한다.
- **기존 ERP '통합 DB 관리' 페이지는 절대 건드리지 않는다.** 새 페이지는 독립 폴더로 추가.
- **ERP 배포는 매번 사용자 승인 후에만.** 1단계는 ERP를 배포하지 않는다(ERP 변경 없음).

## 5. 로드맵 (3단계)

| 단계 | 무엇을 | 보이는 결과 | 흔드는 앱 | ERP 배포 |
|---|---|---|---|---|
| **1단계 — 공용 토대** | 통합 보기의 "계산·설정 로직"과 "앱별 차이를 담는 설정 틀"을 공용 보관함에 **추가**(+간단한 자동 테스트 장치 신설) | 화면 변화 없음. 다음 단계의 안전한 바닥 | 없음(추가만) | 안 함 |
| **2단계 — ERP 새 페이지** | ERP에 별도 새 페이지로 통합 보기를 띄움. ERP가 데이터 주인이라 직접 읽음. 1단계 공용 로직을 첫 소비자로서 검증 | **ERP에서 통합 보기 실제로 보임** ✅ | 없음 | 함(승인 필요) |
| **3단계 — 큰 화면 공용화** | 통합 보기 "큰 화면"을 설정형 공용 부품으로 전환 → 세 앱이 같은 하나를 사용. 하이브·일루아를 공용본으로 교체 | 이후 업데이트가 세 곳에 동일 적용 | 하이브·일루아 전환(회귀 점검) | 함(승인 필요) |

## 6. 1단계 상세 설계 (이번 구현 사이클)

### 6.1 어디에 만드나
- 공용 보관함 저장소 `@wedly/ui-shared`의 새 폴더 `src/unified/`.
- 이미 있는 `src/tiered/`(차수·수식 순수 로직)와 같은 결의 "순수 로직 모음"으로 둔다.

### 6.2 무엇을 옮기나 (옮길 대상은 화면이 아니라 "계산하는 머리")
하이브에 있는 아래 *순수 함수*들을 공용으로 끌어올린다(하이브 복사본은 1단계에선 그대로 둔다 — 3단계에서 공용본으로 교체):

- **묶음·탭 계산** (하이브 `src/lib/unified-sections.ts`):
  - 어떤 칸을 어떤 묶음에 넣고 어떤 순서로 보일지 계산
  - 영역별 세부 탭 목록 만들기
  - "기본정보" 묶음 표준 사양(팀장·팀원·검토보고서 칸 보장 등)
- **탭 순서·이름 적용** (하이브 `src/lib/unified-tab-config.ts`):
  - 저장된 순서·이름을 탭 목록에 입히기
  - 저장값을 안전한 형태로 정규화하기

### 6.3 "앱별 차이를 담는 설정 틀" 정의 (이번 단계의 핵심)
지금은 앱별로 다른 값들이 코드 곳곳에 흩어져 박혀 있다. 이를 **하나의 설정 묶음 타입**으로 정의해, 공용 함수가 "이 앱은 이런 설정이다"를 받아 동작하도록 만든다. 1단계에서 다루는 설정 범위(계산·표시에 필요한 것만):

- 메인(편집 담당) 영역 키 — 예: 하이브 `tax-amendment`, 일루아 `government-subsidy`
- 설정 저장에 쓰는 범위 이름(scope)
- 상단 영역 그룹 목록(경정청구·정부지원금·노무·기업인증·특허 등)
- 맨 앞/맨 뒤 고정 묶음 규칙(기본정보=맨 앞, 파일=맨 뒤)

> 정산 항목 키·계약 칸 정의처럼 "큰 화면"에서만 쓰는 무거운 설정은 3단계로 미룬다(1단계는 작게).

### 6.4 자동 테스트 장치 신설
- 공용 보관함엔 현재 테스트 장치가 없다 → 1단계에 가벼운 단위 테스트 장치(vitest)를 새로 넣는다.
- 옮긴 함수들에 대해 "계산 결과가 이전과 똑같다"를 기계로 확인하는 테스트를 작성(하이브에 이미 있는 탭 설정 테스트 9건을 토대로 이전·확장).

### 6.5 1단계가 "안 하는" 것 (안전)
- 하이브·일루아 코드를 바꾸지 않는다(그들의 복사본은 그대로 동작).
- ERP를 건드리지 않는다 → **ERP 배포 없음**.
- 화면 모양·동작을 바꾸지 않는다(순수 로직 이동 + 테스트뿐).

### 6.6 1단계 완료 기준
- 공용 보관함에 통합 보기 순수 로직 + 설정 틀이 추가되고, 새 테스트가 모두 통과한다.
- 타입 검사 통과, 공용 보관함이 정상적으로 불러와진다(import 가능).
- 다른 앱(하이브·일루아·ERP)은 아무 변화 없음(추가만 했으므로).

## 7. 2단계 개요 (다음 사이클 — 별도 설계서)
- ERP `(erp)` 묶음에 새 폴더(예: `src/app/(erp)/unified-view/`)로 새 페이지 추가. 기존 `/unified-db`는 손대지 않음.
- 1단계 공용 로직을 **첫 실사용 소비자**로서 가져와, ERP의 설정 틀(메인 영역·영역 목록 등)을 주입.
- ERP가 데이터 주인이므로 각 영역을 **직접** 읽는다(외부 빌려오기 불필요).
- 설정 저장 주소 3종(순서·묶음 매핑·탭 설정)을 ERP에도 ERP 로그인/권한 방식으로 추가(하이브 패턴을 따르되 ERP 쿠키·관리자 판정으로 교체).
- ERP는 공용 *화면 부품*(`@wedly/ui-shared`·`@wedly/detail-modal-shared`)을 처음 받아들이게 되므로, 디자인 충돌·불러오기 설정을 이 단계에서 점검.
- **ERP 배포는 사용자 승인 후.**

## 8. 3단계 개요 (가장 신중)
- 통합 보기 "큰 화면"을 설정형 공용 부품으로 끌어올림.
- 하이브·일루아를 공용본으로 교체(각 앱이 공용 부품 최신본을 다시 설치 → 재배포 → 회귀 점검).
- 이때부터 "한 번 고치면 세 곳 동일" 실현.

## 9. 위험·제약 (미리 적어둠)

- **공용 부품 전파가 수동·미고정:** 공용 보관함을 고쳐도 각 앱이 다시 설치해야 반영되고, 지금은 특정 시점으로 고정(핀)되어 있지 않다. 2·3단계에서 "버전 고정 + 설치·재배포 단계"를 의도적으로 둬 안정화한다.
- **두 개의 공용 보관함:** 통합 보기는 `@wedly/ui-shared`와 `@wedly/detail-modal-shared` 둘 다에 의존(미팅·파일·정산 탭). ERP 합류 시 둘 다 받아들여야 함(2단계에서 확인).
- **ERP는 공용 부품 미사용 상태:** 디자인 시스템(자체 방식)과 공용 부품 화면이 섞일 때 모양 충돌 가능 → 2·3단계에서 점검.
- **ERP 운영 민감:** ERP 배포는 매번 사용자 승인. 공용 wedly-erp 프로젝트 권한도 그때마다 확인.
- **회귀 위험은 3단계에 집중:** 하이브·일루아 교체 시 반드시 자가점검 + 동작 비교.

## 10. 범위 밖 (이번에 안 함)
- 하이브·일루아의 통합 보기 코드 교체(3단계).
- 정산·계약 등 "큰 화면" 전용 무거운 설정의 공용화(3단계).
- 로그인 통합·댓글 통합 등 다른 트랙(별도 묶음).
